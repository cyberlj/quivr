# 面试真题

## 二、Agent核心原理

### 1. Agent执行环路（Plan→Act→Observe→Reflect）在生产中如何落地？各环节的异常处理如何设计？
这道题我分两部分回答。第一部分讲执行环路怎么落到生产系统。第二部分讲四个环节的异常怎么治理。我的结论很明确，线上要把 Plan、Act、Observe、Reflect 做成显式状态机和统一执行轨迹，每一步都进入状态、校验、日志和恢复机制。

先说第一个问题，执行环路怎么落地。Plan 负责把任务拆成可执行步骤，至少要产出目标、子任务、停止条件和风险等级。Act 负责执行被授权的工具，模型在这里提供候选动作，真实副作用由执行器接管。Observe 负责把工具返回转成标准事件，并回写到统一状态。Reflect 负责做有限决策，比如继续、改写、重试、降级、转人工。真正上线时，这四个环节要共享同一份任务状态。状态里至少要有当前阶段、最近一次观察结果、已经确认的业务字段、待执行动作、历史事件引用。这样每一步从哪开始、为什么这么做、下一步准备做什么，系统都说得清，也能回放。checkpoint 就是关键节点的状态快照，任务中断后可以从这个点恢复。

再说第二个问题，各环节异常怎么设计。我会按环节拆开处理。Plan 阶段常见问题是目标不清、步骤不可执行、依赖缺失，所以这里要做目标校验、动作空间约束和风险分级。动作空间可以理解成当前这一步允许系统选择的动作集合。Act 阶段常见问题是参数缺失、权限拒绝、接口超时、重复执行，所以这里要做 schema 校验、权限校验、幂等键和超时控制。Observe 阶段常见问题是空结果、脏数据、状态未同步，所以返回结果要写成标准状态、关键字段摘要、原始返回引用，再进入后续推理。Reflect 阶段常见问题是误判、过度重试和错误升级，所以要限制最大步数、重复动作次数，并设置人工接管阈值。

举个典型场景。客服订单 Agent 查询物流时，外部接口超时了。系统此时要保留请求参数、错误类型、是否可重试、上一次状态版本。如果没有这些结构化信息，下一轮 Reflect 很容易继续沿用旧假设，重复调用同一个接口。把异常写回统一状态后，系统才能稳定判断这一轮应该重试、补充订单信息，还是直接转人工。

所以我对这个问题的判断是，生产里的 Agent 环路，本质上是一套受控执行系统。环路能不能稳定，取决于状态是不是统一、异常是不是分层、轨迹是不是可回放。

### 2. ReAct框架在实际开发中，如何避免“思考与行动脱节”？如何优化Reason步骤的准确性？
这道题我分两部分回答。第一部分讲怎么避免 Reason 和 Act 脱节。第二部分讲怎么提升 Reason 本身的准确性。我的结论很明确，线上要把 ReAct 从“交替输出文本”收紧成“基于真实状态的受控决策链”。

先说第一个问题。线上出现脱节，常见有三种表现。第一，推理结论和动作不一致，模型判断应该先补信息，动作却直接去调工具。第二，动作和当前状态不一致，上一步观察结果已经变化，下一步还沿用旧假设。第三，动作本身不合法，比如参数缺失、依赖不满足、权限不够，或者重复执行带来副作用。根因很清楚，推理和执行没有绑定到同一份任务状态上。

解决这个问题，我会做五层约束。第一层，Reason 输出收紧成结构化决策摘要，只保留当前状态、任务目标、下一步动作、动作依据。第二层，建立显式状态，至少包含任务阶段、最近观察、已确认业务字段和可执行动作集合。可执行动作集合就是当前允许系统选择的动作列表。第三层，Act 前做程序校验，检查动作是否合法、工具是否匹配、参数是否齐全、依赖是否满足、权限是否允许。第四层，Observe 后强制回写状态，保留标准状态、关键字段摘要、原始返回引用。第五层，高风险动作单独治理，像写数据库、发消息、创建工单、退款这类动作，都要补幂等键、超时控制和确认条件。

再说第二个问题，怎么提升 Reason 的准确性。我主要看四个方面。第一，轨迹数据质量。高质量样本要体现“基于当前观察做决策”，每一步都引用已知信息。第二，提示词约束。Prompt 要明确三件事：推理只基于当前状态，未知信息需要补齐，动作只来自允许工具集合。第三，观察结果结构化输入。很多工具返回是 JSON、日志、错误码混在一起，先清洗成标准状态和关键字段摘要，推理会稳很多。第四，失败轨迹闭环。线上除了任务成功率，还要拆 tool selection accuracy、parameter fill accuracy、invalid action rate、stale-context rate 这些 step-level 指标。stale-context rate 指模型基于过期状态继续推理的比例。

举个典型场景。客服订单 Agent 收到一句话：“帮我看下这个订单什么时候到。”如果当前状态里没有唯一订单号，合理动作只有两类，请求补充订单信息，或者先查最近订单列表。系统一旦直接调用物流查询工具，就说明推理和执行已经脱节。把状态、动作空间、参数校验和观察回写收紧以后，这类错误会明显下降。

所以我对这个问题的判断是，ReAct 在生产里要靠状态约束、程序校验和轨迹评估站稳，单靠多写几步推理，稳定性上不来。

### 3. Agent工具调用的Schema设计核心是什么？如何保证LLM正确选择工具、传递正确参数？
这道题也分两部分。第一部分讲 Schema 设计的核心。第二部分讲怎么保证模型选对工具、填对参数。我的结论是，Schema 在生产里是一份可验证的工具契约。契约写得清，模型、执行器和权限系统才能对齐。

先说第一个问题，Schema 的核心是什么。核心就是边界清晰、约束可执行、失败可解释。一个能上线的工具 Schema，至少要写清六类信息：工具用途、输入参数、输出结构、前置条件、风险等级、失败语义。参数层还要进一步写清必填项、类型、枚举值、默认值、示例和非法组合。这样模型知道什么时候该调这个工具，执行器知道怎么校验，后面的审计和回放也有依据。比如“查询订单”和“发起退款”这两个动作，从业务上就该是两份完全不同的 Schema，因为它们的副作用、权限要求和失败处理都不同。

再说第二个问题，怎么保证模型选对工具、传对参数。我一般会做四层约束。第一层，工具集合本身要干净。每个工具只负责一件事，描述要短、准、可区分，避免多个工具语义重叠。第二层，调用前先收窄候选集合。系统根据当前状态、任务阶段和权限范围，先给模型一个可选工具列表，减少乱选。第三层，参数生成后做程序校验。这里重点检查字段是否齐全、类型是否正确、枚举是否越界、依赖字段是否成对出现。第四层，执行前再做权限和风险校验。像创建工单、退款、发消息这类有副作用的动作，还要补确认条件、幂等键和审计日志。

这里有个很常见的线上问题。用户说“这个订单我不想要了，帮我处理一下”。如果工具设计含糊，模型很可能直接调退款工具。更稳的做法是把动作拆开。先用查询订单工具确认订单状态、支付状态、退款资格，再决定后面是取消订单、申请退款，还是创建客服工单。参数缺失时，系统要明确告诉模型还缺订单号、退款原因、用户确认状态，后面才有机会继续补齐。

所以我对这个问题的判断是，Schema 设计得好，工具调用就会收敛到受控动作；Schema 设计得松，模型选错工具、传错参数、越权执行的概率都会上升。

### 4. 多步工具依赖如何设计依赖管理、避免重复调用、死循环？
结论是，多步工具依赖要落在显式任务图和执行账本上。任务图负责定义依赖关系，执行账本负责记录每个节点做过什么、做到哪一步、能否重放。这样才能同时解决依赖管理、重复调用和死循环。

依赖管理上，我会把任务拆成节点，节点里明确写 `action`、输入 schema、输出 schema、`depends_on`、前置校验、失败语义和重试预算。DAG 就是有向无环图，适合表示“先查什么，再做什么”的依赖链。执行器每次只放行依赖满足的节点，工具返回统一写回共享状态，状态里至少保留实体字段、状态版本、最近一次观察结果和可执行动作集合。后续节点只从这份状态读取，不靠模型临时回忆。比如订单客服 Agent 里，`query_order` 成功后，`query_logistics`、`check_refund_eligibility` 才能进入候选动作列表。

避免重复调用上，读操作和写操作要分开设计。读操作按 `node_id + normalized_input + state_version` 生成 cache key，命中后直接复用结果。写操作带幂等键，幂等键一般由业务实体 id、动作类型、请求摘要组成，数据库侧再配唯一约束或状态表。执行账本要记录 `pending`、`running`、`succeeded`、`failed`、`skipped` 这些状态，以及参数摘要、trace id、结果引用和错误码。这样任务重试、服务重启、人工恢复时，系统能判断这个节点该继续、该跳过，还是该重新执行。

死循环治理要看计划层和运行层两处。计划层先做图校验，检查循环依赖、缺失依赖、永远无法满足的前置条件。运行层再做三类保护：最大步数上限、同一节点重复执行上限、无进展检测。无进展检测指连续多步后关键状态没有变化，比如订单号、权限状态、候选结果数量都没变，系统还在重复查单，这时就该结束自动链路，转成补信息、降级回复或人工接管。反思节点也要受约束，只有看到新的观察结果或者新的状态版本，才允许重新规划。

一个典型场景是“帮我处理这笔订单退款”。系统通常要先查订单，再查支付状态，再校验退款资格，最后创建售后工单或发起退款。如果没有任务图，模型很容易跳步；如果没有幂等键，创建售后工单时网络抖动一次就可能重复建单；如果没有无进展检测，资格校验失败后可能反复查同一张订单。生产里把这三层收紧，链路才会稳定。

### 5. Agent的反思机制（Reflection）如何实现？如何让Agent从执行失败中学习？
回答分两部分。第一部分讲 Reflection 怎么实现。第二部分讲执行失败后怎么沉淀成学习闭环。

先说第一个问题。Reflection 在线上更像结构化诊断节点，作用是解释失败、修正下一步动作、给执行器提供可消费结果。它通常挂在失败、低置信度、超预算、重复动作这些节点后面，输出 schema 至少包含 `failure_type`、`root_cause`、`evidence`、`proposed_fix`、`confidence`、`state_patch`、`should_retry`、`need_handoff`。`state_patch` 就是需要回写状态的修正字段，比如订单号缺失、退款原因缺失、权限未通过。执行器拿到这份结果后，才知道下一步是补字段、换工具、重排计划，还是结束任务。

再说第二个问题，怎么从失败里学习。这里可以拆成任务内学习和跨任务学习。任务内学习只影响当前 run，重点是修改状态、收缩动作空间、调整参数、替换下一步动作。跨任务学习走离线闭环，把失败轨迹进入错误库，按错误类型打标签，比如工具选择错误、参数缺失、Observation 误读、状态过期、循环过深。后面的 prompt 调整、few-shot 更新、工具 schema 改造、评测集扩充，都从这个错误库取样。few-shot 指少量高质量示例，用来约束模型在相似情境下的决策。

风险控制也要一起建。Reflection 自己也可能判断错，所以它的权限要受限，通常只允许修改局部状态和下一步动作建议。连续两次给出同一根因、同一修正动作时，系统就该转向补信息、降级或人工介入。日志里要保留原始失败事件、Reflection 输出、采纳结果和后续效果，后面才有条件回放和评估。

工单场景里很直观。用户说“帮我查下这个售后怎么还没处理”，系统第一次查不到工单。Reflection 如果输出“根因是缺少工单号，证据是检索结果为空且话语里没有唯一标识，修正动作是先查最近售后记录”，这条结果一方面能推动当前任务继续，另一方面也能进入失败样本库，后面用于训练和评测相似场景。

### 6. Agent的短期记忆、长期记忆如何设计存储结构？如何平衡记忆容量与查询速度？
回答分两部分。第一部分讲短期记忆和长期记忆怎么存。第二部分讲容量和查询速度怎么平衡。

先说存储结构。线上我通常拆三层。第一层是会话短期记忆，保存最近几轮对话、最近一次工具结果摘要、当前意图和关键槽位。槽位就是结构化字段，比如订单号、时间范围、用户身份、待确认项。第二层是工作记忆，服务当前任务执行，里面放任务状态、计划节点、已确认事实、候选动作、状态版本和 checkpoint。第三层是长期记忆，保存稳定偏好、历史案例、文档知识和规则。三层存储可以分别落在 Redis、关系库或 KV、向量库和关系库组合。

记忆条目本身也要统一 schema。一个实用字段集合可以是 `memory_id`、`scope`、`type`、`content`、`embedding_ref`、`source`、`version`、`ttl`、`created_at`、`updated_at`、`confidence`、`status`。`scope` 用来区分 user、session、task、tenant；`version` 用来标识同一事实的更新；`status` 可以设成 active、expired、revoked、suspected_pollution。污染校验也要加两道。写入前检查来源可信度、敏感字段、跨租户风险、冲突版本；读取后再检查和当前状态是否冲突，避免把旧订单状态、别的用户偏好、注入内容带回上下文。

再说容量和速度。关键抓手是分层写入、分层检索和明确淘汰规则。短期记忆按 TTL 和轮次窗口淘汰，工作记忆跟任务生命周期绑定，任务结束后保留摘要和引用，长期记忆按价值、时效、命中率做分级存储。检索时优先走精确过滤，再做语义召回，当前任务强相关信息先查工作记忆，长期知识再按租户、标签、时间、版本做过滤。热点条目走缓存，冷条目保留引用 id，需要时再展开原文。

评估也要一起建。记忆层至少看 write reject rate、memory hit rate、stale hit rate、expire rate、conflict rate、污染拦截率和 retrieval latency。`memory hit rate` 指检索出的记忆最后被真正使用的比例，`stale hit rate` 指命中了已过期或已被新版本覆盖的条目。客服退款场景里，如果长期记忆里还留着旧售后规则，系统就可能给出过期答案，所以版本管理和过期率监控都很关键。

### 7. 高并发场景下，Agent任务排队、限流、优先级调度如何实现？
这题有三个子问题。排队、限流、优先级调度都要围绕同一套任务状态机来设计，客服、工单这类高峰流量场景尤其明显。

先说排队。入口先做 admission control。这个词的意思是请求进系统前先做准入判断，看租户配额、并发位、预计 token 成本、外部工具额度、超时预算够不够。通过后任务进入状态机，常见状态可以设成 `queued`、`running`、`waiting_tool`、`paused`、`retry_wait`、`cancel_requested`、`cancelled`、`done`、`failed`。在线客服查单、创建工单、夜间报表生成要拆成不同队列，因为它们的 SLA 不一样。SLA 就是服务等级目标，核心看延迟、成功率和可用性。

再说限流。限流要分租户、用户、模型、工具四层。令牌桶适合处理突发流量，它会按固定速度发放令牌，请求拿到令牌才准入；并发阈值适合限制同时运行中的任务数；工具级限流负责保护物流接口、工单接口这类下游依赖。任务进入 `running` 后，如果某个工具额度耗尽，可以切到 `waiting_tool` 或 `retry_wait`，避免整个任务直接失败。取消语义也要提前定义。用户主动取消时，任务状态切到 `cancel_requested`，调度器停止发新动作；已经发出的副作用节点继续等待确认，再决定是否补偿。

最后说优先级调度。客服场景里，查订单和创建工单属于前台交互任务，优先级高；摘要生成、失败重放、离线评估属于后台任务，优先级低。调度器可以用 weighted fair queuing，也就是按权重公平分配服务份额，再配合 aging 机制，让低优先级任务等待太久后逐步提升权重。恢复和回放语义也要分开。恢复是拿 checkpoint 和执行账本继续跑原任务；回放是复现当时的输入、状态和工具返回，用来排障或评估，通常不会再次触发真实副作用。

评估上至少看队列长度、平均等待时长、放弃率、取消成功率、恢复成功率、P95 延迟、429 比例、工具排队时长和调度公平性。双十一客服高峰时，如果查订单任务长期卡在 `queued`，工单创建任务频繁落到 `retry_wait`，调度看板会很快把问题暴露出来。

### 8. Agent调用工具超时，如何设计重试策略、熔断机制、降级方案？兜底回复如何设计才不生硬？
结论是，工具超时治理要先判断这个动作有没有副作用，再决定重试、熔断和降级怎么配。执行链路和用户回复要同时设计，否则系统内部处理得再完整，用户体验还是会很差。

重试策略上，我会先给每个工具定义超时预算、可重试错误类型和最大重试次数。读操作通常可以重试，写操作要先确认幂等边界。重试采用指数退避加抖动，指数退避指等待时间逐次增加，抖动指加入随机量，避免大量请求同时回流。重试前还要校验状态版本，避免上一步结果已经变化，系统还按旧状态继续打同一个接口。

熔断机制用来保护故障依赖。常见阈值包括超时率、错误率、429 比例、连续失败次数。达到阈值后进入 open 状态，暂停把新流量送进故障工具；一段时间后进入 half-open，也就是用少量探测流量测试依赖是否恢复；恢复正常后再 close。熔断状态本身也要写进 Agent 状态和监控系统，后续规划时才知道这个工具当前不可用。

降级方案要按工具类型准备。查询类工具可以切备用数据源、读缓存、返回最近一次成功快照。写入类工具更适合进入人工确认链路、延迟重试队列，或者改成创建待处理工单。兜底回复要把过程说清楚，至少包含三类信息：已经完成的步骤、当前卡住的环节、系统接下来的动作。比如“订单已经确认存在，物流接口当前超时，我会继续尝试一次；如果还失败，会转给人工客服继续处理。”这类回复更自然，也能降低用户不确定感。

典型场景是物流查询。系统先查到订单存在，再调物流接口超时。如果直接回一句“系统繁忙，请稍后再试”，用户会觉得这次对话没有推进。更稳的做法是把已确认的事实保留下来，再告诉用户当前障碍和下一步处理方式。

### 9. Agent生成的SQL/代码需要执行，如何设计沙箱环境、权限隔离，避免越权操作、注入攻击？
结论是，SQL 和代码执行链路必须把“生成候选语句”和“执行真实副作用”硬隔离。模型只负责提出候选方案，真正的执行由沙箱、权限系统和策略引擎共同决定。

SQL 场景里，我会先做 schema 约束和语法解析，再做权限和风险校验。输入侧优先用参数化模板，避免把用户原始文本直接拼进 SQL。执行前做 AST 校验，AST 是抽象语法树，用来分析这条 SQL 访问了哪些表、用了哪些操作、有没有危险子句。账号权限默认只读，表和字段走白名单，租户过滤、行级权限、时间范围上限都在执行器层强制注入。对高成本查询再补 explain 或成本估算，拦截全表扫描、大范围 join 之类高风险语句。

代码执行场景要放进隔离运行时，比如容器或 microVM。microVM 是隔离强度更高的轻量虚拟机。运行时要限制网络访问、文件系统写权限、CPU/内存/磁盘配额、执行时长和可用系统调用。import 白名单、命令白名单、环境变量隔离、只读依赖目录都要配置上。执行前做静态分析，执行后保留 stdout、stderr、退出码和资源消耗日志，方便回放和审计。

越权和注入防护要贯穿整条链路。用户身份从后端认证系统换成短时、最小权限的能力票据，模型上下文只拿到脱敏后的权限摘要。原始数据库账号、访问令牌、内部地址都不能进 prompt。审计日志至少保留用户 id、租户、原始意图摘要、生成语句摘要、校验结果、是否执行、执行结果和 trace id。这样线上出现风险操作时，既能拦下来，也能追溯是谁在什么上下文里触发的。

Text2SQL 是很典型的例子。用户问“查最近一个月退款订单 top10”，系统可以生成候选 SQL，但执行器还要继续检查库表权限、时间范围、返回行数限制和排序字段。用户如果输入“顺便把这张表删了”，AST 校验和账号权限会直接把这条语句拦在沙箱外。

### 10. LangChain、LangGraph在生产中如何选型？LangGraph的状态机设计如何适配复杂业务流程？
这题分两部分。先讲 LangChain 和 LangGraph 怎么选。再讲 LangGraph 的状态机怎么贴合复杂业务流程。

先说选型。客服查单、退款资格判断、工单转人工这类链路，一开始就带状态、分支和人工介入，所以我会优先看状态机能力。LangChain 更适合顺序清楚的链路，比如检索、总结、输出这种线性流程；LangGraph 更适合节点多、条件分支多、需要恢复和回放的场景。这里的状态机可以理解成“当前任务处在哪个阶段、满足什么条件才能走到下一步”的显式规则集合。业务一旦涉及退款审核、工单补材料、人工批准，图模型会更贴近真实流程。

再说状态机设计。以售后客服为例，节点可以拆成 `classify_intent`、`query_order`、`check_refund_policy`、`create_ticket`、`waiting_human`、`notify_user`。状态对象里至少要有 `current_stage`、槽位字段、最近观察结果、已执行动作、状态版本、checkpoint、人工介入标记。每个节点都定义输入 schema、输出 schema、失败语义、超时策略和是否有副作用。条件边写清楚转移条件，比如订单存在且在售后期内才进入退款校验，证据不足就进入补材料节点，低置信度就进入人工审核。

工程上我会把框架限制在编排层，把权限、审计、幂等、日志、回放、指标、身份透传放在外部控制层。这样做的原因很直接，复杂业务里的风险点主要集中在副作用和恢复。比如 `create_ticket` 这种节点如果被重放，系统必须依靠幂等键和执行账本判断是否已经创建过工单。客服链路的业务对象会贯穿设计本身，图里的每个节点都对应一个真实动作，后续回放、排障和指标统计都会更清楚。

### 11. Agent执行过程如何做可观测？每一步的思考、工具调用、耗时、Token消耗、异常，如何全链路追踪？
可观测要同时建 trace、结构化日志、聚合指标三层。trace 解决“链路在哪断了”，日志解决“当时到底发生了什么”，指标解决“问题是不是在持续扩大”。

全链路追踪上，一次任务通常拆成 `run -> step -> tool_call` 三层。`run` 是整次任务实例，`step` 是一次规划、决策、反思或状态转移，`tool_call` 是一次具体工具调用。每一层都是一个 span。span 可以理解成带开始时间、结束时间、状态和上下文的一段执行区间。三层 span 用同一个 `trace_id` 串起来，再挂 `run_id`、用户 id、租户 id、任务类型、状态版本。思考过程更适合落“决策摘要”，比如本步选了什么动作、引用了哪些状态、置信度大概多少，线上很少直接保存完整思维链。

日志字段要围绕回放来设计。常见字段包括 prompt 版本、模型版本、输入摘要、工具名、参数摘要、输出摘要、token、耗时、费用、错误码、重试次数、幂等键、checkpoint id。Token 指模型处理文本时的基本计量单位，和成本、延迟都强相关。工具原始返回体通常只保留引用或脱敏摘要，避免日志成本和安全风险一起放大。高风险动作像退款、发消息、创建工单，还要额外记录审批状态和操作者。

指标层至少看任务成功率、P95 延迟、tool error rate、retry rate、loop rate、handoff rate、token per run、cost per success。P95 指 95 分位延迟，也就是 95% 的请求都快于这个时间，适合观察长尾。客服系统里如果 `query_order` 工具的超时率突然升高，trace 会告诉你慢在哪一步，日志会告诉你参数和状态是什么，指标会告诉你问题有没有扩散到整条链路。

### 12. 多个用户同时触发同一个Agent任务，如何做幂等设计，避免重复执行？
幂等设计要覆盖请求指纹、任务去重、副作用收敛三层。多个用户同时触发同一个 Agent 任务时，系统需要先识别是不是同一类任务，再决定能不能共享结果，最后收住真实副作用。

第一层是请求指纹。指纹通常由租户、任务类型、归一化意图、关键实体、权限范围、时间窗口和状态版本组成。归一化意图指把不同说法映射成同一条任务语义，比如“查物流”和“看配送到哪了”。权限范围必须进指纹，否则两个权限不同的用户可能命中同一份结果。

第二层是任务去重。查询类任务可以建 in-flight registry，也就是在途任务登记表。新请求先查有没有同指纹任务正在执行，如果有，就挂接等待同一结果，或者复用最近一次结果。耗时长的任务可以再加分布式锁和结果缓存，避免并发拉起多条相同链路。任务表里要记录 `fingerprint`、`status`、`owner`、`expire_at`、`result_ref`、trace id 和状态版本，服务重启后还能恢复判断。

第三层是副作用收敛。创建工单、发送消息、发起退款这类写操作都要带幂等键。幂等键通常绑定业务实体 id 和动作类型，比如 `ticket:order_123` 或 `refund:order_123`。数据库侧再配唯一约束或状态机，保证重复请求最多只落一次真实动作。执行器日志里还要保留参数摘要、外部请求 id 和结果引用，后面排查重复执行时才能快速定位。

客服并发建单就是典型场景。多个客服同时点“为这笔订单创建售后工单”，查询结果可以共享，创建工单这一步必须只成功一次。把请求指纹、在途复用、幂等键都做好，线上就能把重复副作用压到很低。

### 13. Agent如何安全传递用户身份（登录态、权限），调用工具时避免身份泄露、越权？
回答分两部分。第一部分讲身份和权限怎么安全传递。第二部分讲怎么防泄露、越权，以及怎么评估这套机制是否可靠。

先说传递链路。原始登录态应该留在后端认证域，Agent 链路里流转的是 capability token，也就是能力票据。票据 schema 我会要求至少包含 `token_id`、`subject`、`tenant_id`、`delegator`、`resource_scope`、`allowed_actions`、`issued_at`、`expire_at`、`nonce`、`trace_id`、`policy_version`。`delegator` 用来表示是谁委托了这次调用，适合做委托链审计；`nonce` 是一次性随机数，用来防重放。认证系统先完成用户校验，再由 credential broker 做 token exchange，把原始 Cookie 或 Access Token 换成短时、最小权限、工具专用的能力票据。模型上下文里只保留脱敏后的权限摘要，比如“这个用户能查自己订单，能创建工单，退款需要二次确认”。

再说防泄露和越权。网关层做租户、资源、动作三重校验，业务服务再做对象级校验，比如这笔订单是不是当前用户的订单，这份文档是不是当前部门可访问。高风险动作再检查确认状态、审批状态和 `policy_version`。票据生命周期也要完整管理，包括 active、expired、revoked 三类状态。用户退出登录、权限收回、工单转交后，revocation 列表要能立刻生效。重放防护靠三件事：短 TTL、nonce、服务端去重窗口。日志里保留 `token_id`、`delegator`、`subject`、`resource_scope`、结果码、trace id 和策略版本，方便做委托链审计和越权排查。

风险点主要有四个。第一，prompt 注入把系统提示或工具回包里的敏感字段再吐给模型。第二，日志泄露把请求头和原始响应打进可检索日志。第三，票据过期或被吊销后还在继续使用。第四，重复发送同一票据造成重放攻击。处理方式要成体系：敏感字段脱敏，原始凭证永远不进 prompt，日志走白名单字段，网关实时查 revocation 状态，所有工具请求都校验 nonce 和时间窗口。

评估这套机制时，我会看 unauthorized request rate、revocation propagation latency、replay blocked rate、delegation audit completeness。`revocation propagation latency` 指吊销指令从控制面传到所有执行节点的时间，`delegation audit completeness` 指委托链是否能从用户到工具调用完整追溯。企业知识库和订单客服都适合这样做，因为两类场景都同时要求细粒度权限和完整审计。

### 14. 如何实现Agent执行过程的可回放、可打断、可人工干预？
结论是，可回放、可打断、可人工干预的底座都是事件流、状态快照和外部可控状态机。只要执行过程还藏在内存里，这三件事都做不稳。

可回放依赖事件溯源。事件溯源指把每次状态变化记录成不可变事件，再配合 checkpoint 做快照。每一步计划、工具调用、观察结果、状态转移、人工操作都要记录事件，事件里至少包含输入摘要、输出摘要、状态版本、节点 id、trace id、模型版本、prompt 版本和工具版本。回放时可以按事件顺序重建状态，也可以把工具层替换成 mock 返回，用来排查“当时为什么走到这一步”。

可打断本质上是安全暂停。系统收到取消或暂停指令后，调度器先停止分发新动作，再把当前节点标记为 `paused` 或 `cancel_requested`。对已经发出的副作用动作，要靠幂等键和状态确认避免重复落地。恢复时从最近 checkpoint 继续，结合执行账本判断哪些节点已经成功、哪些节点需要补偿、哪些节点要重新执行。这样服务重启、用户刷新页面、人工接管都不会把链路搞乱。

人工干预要成为正式状态，而不是临时备注。常见做法是引入 `waiting_human`、`manual_override`、`approved`、`rejected` 这类状态。人工可以补字段、修改计划、批准高风险动作、直接终止任务，所有操作都写成事件并带操作者信息。恢复执行时，系统读取新的状态版本继续往下走。比如退款 Agent 卡在“退款原因缺失”，人工补齐原因后，任务直接从校验节点继续，不需要从头再跑一遍。

这套机制在线上很重要。工单、退款、审批这类链路天然会遇到中断和人工介入。把事件、快照、状态机做扎实，系统才有真正的可恢复性。

### 15. Agent的任务分解能力如何优化？如何让Agent正确拆分复杂任务？
任务分解的目标是产出一张可执行、可校验、可终止的任务图。子任务边界清楚，后面的工具调用、状态推进和评测才会稳定。

正确拆分复杂任务，第一步是把分解结果收紧成结构化 schema。每个子任务至少要写 `goal`、输入、输出、`depends_on`、候选工具、完成标准、失败后的回退策略。完成标准要足够具体，比如“拿到订单号并校验存在”这种表达，执行器和评测器都容易判断。子任务粒度最好接近一次模型决策或一次工具动作。

优化分解能力通常有四个抓手。第一，用高质量示例告诉模型拆到什么粒度、依赖怎么表达、什么叫完成。第二，引入 planner-verifier 双阶段，planner 负责提出任务图，verifier 负责做 schema 校验、依赖校验、工具可用性校验和循环检测。第三，先抽实体和约束，再做计划，比如先识别订单号、时间范围、用户权限，再决定后续步骤。第四，把失败分解轨迹回灌到 few-shot 和评测集，持续纠正拆分过粗、拆分过碎、顺序错误这些问题。

风险点主要集中在粒度失衡。拆得过粗，后续步骤内部还藏了很多决策，治理难度会上来；拆得过碎，链路会变长，token 成本和失败点都会增加。生产里通常会给计划加预算，比如最大子任务数、最大深度、最大并行度，再结合业务模板收敛自由度。订单客服、工单流转、报告生成都适合沉淀领域模板。

比如“帮我分析这周售后投诉增多的原因并给改进建议”，更稳的拆法是先拉工单数据，再分类聚类问题，再抽高频原因，再生成建议。这样每一步都有明确输入输出，后面做校验和回放也容易。

### 16. 开源Agent框架在生产中落地的坑有哪些？如何规避？
回答分两部分。第一部分讲开源 Agent 框架在生产里的常见坑。第二部分讲规避方式，以及上线前后怎么验证这些规避动作有没有真正生效。

先说常见坑。客服退款、工单流转这类链路最容易暴露框架问题，因为状态多、副作用多、人工介入多。第一类坑是隐藏状态，节点上下文、memory、自动重试散在框架内部，回放和排障都困难。第二类坑是升级漂移，框架版本一变，prompt 拼装、工具路由、序列化格式、默认重试策略都可能跟着变化。第三类坑是默认链路偏重，框架为了通用性加了不少线上并不需要的步骤，成本和时延都会被拉高。第四类坑是治理能力不足，权限、幂等、日志脱敏、人工接管这些生产要素需要自己补。

再说规避。我的做法通常是把框架收缩到编排层，状态存储、身份透传、权限校验、审计日志、回放、指标、重试、熔断都放进自己的控制层。自动 memory、自动 retry、默认 prompt、内置 parser 这些容易藏逻辑的功能，线上尽量显式配置或直接关闭。像退款链路里的 `create_ticket`、`submit_refund` 这种副作用节点，我会强制走自己的执行器和幂等账本，不把最终副作用托管给框架默认行为。

验证规避是否生效，分上线前和上线后两段。上线前做回归测试、轨迹 diff、故障注入和版本对比。轨迹 diff 指同一组输入在新旧版本下比较状态转移、工具选择、token 消耗和终态差异。故障注入就是主动制造超时、429、空返回、脏数据，看框架外部控制层能不能把问题收住。上线后重点看四类指标：框架升级前后成功率变化、token 变化、重复副作用次数、异常回放可还原率。如果升级后客服退款链路的重复建单率上升、轨迹回放率下降，就说明规避动作没有完全生效。

所以这类框架的工程判断很直接：开发效率可以借框架，生产控制权要留在自己手里，验证也要用轨迹和指标来证明，而不是只看功能能不能跑通。

### 17. Agent与现有后端系统（Java/Go）对接，如何保证接口调用的稳定性、一致性？
这题也分两部分。先讲 Agent 和 Java/Go 后端怎么保证接口调用稳定。再讲跨服务链路里怎么守住一致性，以及怎么评估这套机制。

先说稳定性。订单、支付、工单这类后端服务已经有成熟边界，所以 Agent 接入时我会坚持 contract-first，也就是先定义清楚 API 或事件契约，再接编排层。契约至少包含输入输出 schema、错误码、超时预算、幂等键、版本策略和降级语义。Agent 侧统一走 SDK 或网关，参数校验、重试、熔断、trace 透传都在这一层收口。读操作尽量保持纯查询，写操作走明确的命令接口，避免让 Agent 直接拼 RPC 参数或数据库语句。

再说一致性。单服务内部靠本地事务，多服务链路通常靠 Saga 和 Outbox。Saga 是把一条业务流程拆成若干可补偿步骤，某一步失败后执行补偿动作或挂起等待人工处理。Outbox 是在本地事务里同时写业务数据和待发送事件，再由异步投递器统一发消息，解决“库写成功了，消息没发出去”这类问题。退款链路很典型：订单服务把状态改成退款中，支付服务发起退款，工单服务记录售后单。Agent 编排层要把每一步命令结果、补偿状态、人工接管状态都写进任务状态机和执行日志。

风险主要有三类。第一，模型自由度过高，把参数漂移带进后端边界。第二，跨服务写操作缺少补偿，链路会停在半完成状态。第三，对账和回放能力不足，线上出了差错很难定位。对账就是定期把订单状态、支付状态、工单状态拉到一起核对，发现跨系统不一致。回放是用原始输入、状态快照、事件日志复现当时的执行过程，看问题出在编排层还是后端服务。

评估时我会看 command success rate、compensation success rate、reconciliation mismatch rate、replay recoverability。`compensation success rate` 指补偿动作最终成功闭环的比例，`reconciliation mismatch rate` 指对账时发现状态不一致的比例。退款场景里，如果支付已经退了，订单状态还停在“退款中”，对账会第一时间暴露问题；如果异常回放还原不出当时的参数和状态，后续定位成本会很高。

### 18. 如何评估Agent的任务完成率？生产中如何统计Agent的成功率、错误率、步骤合理性？
Agent 评估至少要拆成结果层、过程层、业务层三层。任务完成率回答“目标有没有达成”，成功率和错误率回答“系统稳不稳”，步骤合理性回答“这个结果是不是通过合理路径拿到的”。

任务完成率先定义终态。终态也就是任务结束时的标准状态，常见有 `success`、`partial_success`、`handoff`、`user_cancelled`、`system_failed`、`policy_blocked`。不同任务的成功标准不同，查单看是否找到正确订单并回答核心问题，退款看资格判断和状态推进，工单看是否创建到正确对象并写入正确分类。终态先定清楚，统计口径才稳定。

成功率和错误率要同时看 run 和 step 两层。run 层反映整次任务是否完成，step 层反映每一步是否合理。常见 step-level 指标包括 `tool_selection_accuracy`、`parameter_fill_accuracy`、`invalid_action_rate`、`loop_rate`、`stale_context_rate`、`retry_rate`。`tool_selection_accuracy` 指选工具是否选对，`invalid_action_rate` 指当前状态下发起了不该发起的动作，`stale_context_rate` 指模型拿着过期状态继续推理。数据来源一部分来自规则校验和程序日志，一部分来自线上抽样标注、失败回放和人工审查。

步骤合理性重点看四件事：工具有没有选对，参数有没有填对，步骤有没有冗余，状态有没有倒退。这里也可以用 LLM-as-judge 做辅助评分。LLM-as-judge 指让另一套模型根据规则和参考答案，对步骤质量做辅助判断，但关键业务通常还需要人工抽样复核。比如客服 Agent 最终把工单建出来了，但中间重复查了三次无关订单，还走错了一次工具，这类 run 在结果层算成功，在过程层只能算低质量成功。

统计链路一般是事件日志加评测看板。每个 run、step、tool_call 都带 trace id、任务类型、版本号和终态，离线聚合成任务完成率、错误率、人工接管率、P95 时延、cost per success。再把高频失败样本持续回灌到评测集，评估口径会越来越贴近真实业务。

## 三、RAG生产落地痛点题

### 1. 百万级文档RAG，检索延迟要求 <200ms，如何设计索引、分片、缓存架构？（结合 quivr 项目实例）

这个问题，首先要分解检索的全链路，看各环节延迟通常出现在什么地方，在哪些步骤百万级文档会让延迟变得尤为突出，再提出具体缓解方案。以 quivr 项目为例，具体分析如下：

#### 一、检索各环节延迟分布

一般 RAG 检索流水线包含：
1. **Query 预处理**：归一化、意图识别、query 重写等，通常时间可控，除非外部 LLM 参与。
2. **分片路由**：输入 query 后要判定命中哪些分片、workspaces、collections。这一步数据量极大时若分片层次乱，筛选环节尾延迟会上升。
3. **主召回（ANN 近邻检索）**：这是百万级文档下通常最慢的环节。每多一个分片、向量库规模越大、效率越受限制，尤其是磁盘型后端或分布式模式，P95 延迟会上飙。
4. **元数据/权限过滤**：规模大时如果过滤条件后置，会制造长管道/误命中，影响整体性能。
5. **Chunk 加载**：检索到 chunk id 后还需批量加载正文，IO 压力大时容易偶发慢查。
6. **重排/后处理**：通常为轻量化 rerank，但多路合并时部分模型重排也有不小延迟。
7. **缓存命中或失效判断**：如果 key 设计不优，缓存命中率低，系统频繁走主链路。

#### 二、百万级规模下，延迟最易激增的环节

- **高并发的 ANN 检索**：百万量级的向量库，单分片就可能遇到 IO 争用、内存不够、ANN 精度与速度权衡带来 P95 尾延迟提升。
- **分片路由和合并**：分片设计不科学，query 会打穿太多分片，每个分片单独检索+合并，整体链路叠加延迟。
- **Chunk 批量加载**：命中大批量 chunk 时，正文远程拉取、分布式读 IO 会不稳定。

#### 三、quivr 项目中的思路与缓解手段

1. **优先分片路由，精准命中小规模向量库**
   - quivr 支持 collection/workspace 级分组，可以根据租户、知识库类型、热度等预分片，避免大表全量检索。
   - 实现细粒度分片映射表，query 先大致过滤可疑分片，只检索命中的分区，剩下交并集合并结果，大幅降低主链路压力。
2. **高效向量索引与异构存储配置**
   - 热点分片、活跃 chunk 建议用内存型 faiss/hnsw，极大加快 ANN 检索；冷数据可用磁盘型或分布式后端，通过异步刷新缓慢回收。
   - 各分片定期评估 embedding 空间分布，防止向量漂移，一旦发现检索热点倾斜及时动态重分片。
3. **多级缓存加快命中，有效降低主链路压力**
   - quivr 层面可设计三类缓存：
     - 查询归一化与 rewrite 层（减少重复 query 下游压力）；
     - 检索召回结果层（带上 query、权限、分片/索引版本等多维 key）；
     - chunk 内容层（热点 chunk 正文预缓存，减少批量 IO）。
   - 缓存失效依赖 TTL+分片/索引版本号双因子管理，保证知识更新能细粒度使当前缓存失效，老数据不会拖慢响应。
4. **权限与元数据前置过滤，避免后置结果回刷、误下发**
   - 权限相关的字段 hash 进缓存 key，或者索引时预分组，能让缓存与检索环节只服务合法对象，减少无效环节。
5. **合理 fallback 与延迟控制**
   - 对特别大请求、意外慢分片支持部分降级策略（如只合并部分分片 topK，超时 fallback 到上次缓存结果），保证响应时间稳定可控。

#### 四、策略举例

- 对检索延迟提升最敏感的 collection（如规则制度库），必须配置更细分片与更高频缓存更新，必要时 chunk 提前预热进内存。
- 索引构建、分片表动态维护、回源拉取等任务建议异步后台执行，主链路只走最快分支。

#### 总结

结合 quivr 项目经验，百万级文档下检索延迟本质瓶颈集中在召回与数据分片、缓存命中。最有效的缓解就是：
- 精细分片、召回优选热点分区、
- 充分利用多层缓存并做好版本失效精准触发、
- 权限和元数据过滤靠前并纳入 key 管理、
- 有选择的分级存储与优先加载。

形成工程上“快主链、慢分支、冷数据降级”的结构，可最大化保障 <200ms 的检索延迟目标。

潜在要求：召回质量


回答我按索引、分片、缓存三层展开，因为题目本身就在问这三个点。先把场景放清楚：企业客服知识库里有上百万份制度文档、工单 SOP、产品说明，客服坐席在对话中问“退款规则是什么”“这个工单该转哪个队列”。这里的硬约束是检索链路要压到 200ms 以内，所以工程取舍会很明确，优先保证稳定时延，再在这个边界内争取召回质量。全库大广播和大规模重排都不适合这条链路。

先说索引。在线链路我会做三层索引。**第一层是元数据过滤索引**，先按 `tenant_id`、知识库、文档类型、时间范围、权限标签把候选集合压小。第二层是双路召回索引，一路倒排，一路向量。倒排适合命中工单号、错误码、产品名、制度标题；向量适合命中口语化问题和同义表达。ANN 是近似最近邻检索，用更低成本找相似向量。热数据我会放 HNSW 这类内存型索引，冷数据放 IVF-PQ 这类压缩索引，因为 200ms 约束下，热数据的低延迟比全量高精度更重要。第三层是重排层，只对几十条候选做 rerank，不会把上百条结果都送进去。这样做的原因很简单，重排质量再高，候选一多，长尾时延就会明显抬头。

再说分片。主分片我会按租户和业务域切，比如客服知识库、法务制度库、内部工单库分开；子分片再按时间或热度切，把近 30 天高频更新文档放热分片，老文档下沉到冷分片。这里要避免跨分片 fan-out。fan-out 可以理解成一次查询同时打到很多分片，分片越多，网络开销、聚合开销和长尾抖动越大。线上入口会维护一张分片路由表，先根据 `tenant_id`、`kb_id`、`domain`、`time_bucket` 算出目标分片，再决定查哪些节点。权限过滤 bitmap 也可以提前放到分片侧。bitmap 就是一张位图，用来快速表示“哪些 chunk 当前用户或用户组能看”，这样权限过滤可以前置，不会等召回完再裁掉一大半结果。

最后说缓存。这里我会放三层缓存。第一层缓存 query rewrite、实体抽取、时间表达归一化。第二层缓存检索结果，也就是召回后的 chunk id、分数、命中的分片。第三层缓存对象正文，比如 chunk 文本、标题、版本、权限摘要。缓存 key 至少要带 `tenant_id`、`user_scope_hash`、`normalized_query`、`filter_hash`、`index_version`、`rerank_version`。`user_scope_hash` 代表权限范围摘要，作用是防止不同权限用户命中同一份缓存。对高频问题，还会做 query routing。query routing 指系统先判断问题类型，再决定走轻链路还是重链路。比如“退款规则是什么”这种简单问题，可以走倒排加缓存；“某个跨国客户的售后政策例外怎么判”这种复杂问题，再走向量召回和重排。

200ms 预算我会在开头就拆死，通常是过滤 10 到 20ms，召回 40 到 80ms，重排 40 到 60ms，结果组装 20 到 30ms，剩下留给网络和排队抖动。这个预算下，我接受局部召回优先于全局穷举，也接受简单 query 走轻链路，复杂 query 才走重链路。因为在线客服场景看的是 P95，平均值漂亮意义不大。

这套设计最容易出问题的地方有四个。第一，分片键选得不好，热点租户把某几个节点打满。第二，权限过滤放在召回后面，既拖时延，也会放大越权风险。第三，缓存 key 设计不完整，跨用户串结果。第四，重排候选集放得太大，P50 好看，P95 很差。

效果和系统面我会一起盯。系统侧看 P50、P95、缓存命中率、分片 fan-out、热点分片负载、重排耗时。这里的 fan-out 就是一次查询命中的分片数。效果侧看 Recall@K 和 NDCG。Recall@K 指前 K 个结果里，召回到了多少本该命中的相关文档；NDCG 看的是排序质量，高相关结果排得越靠前，分数越高。企业知识库上线前我会用真实历史 query 做回放，把延迟、召回、权限过滤一起压测。这样才能知道这套架构到底是在省时间，还是在偷召回。

### 2. 文档频繁更新/删除，向量库如何保证实时一致性？如何避免召回旧知识、脏数据？
这个问题我会按三个子问题回答，因为线上故障也正好分成这三类。场景还是企业客服知识库。法务今天更新了退款政策，运营删掉了过期 FAQ，客服一分钟后还会继续检索。如果链路没收紧，坐席会查到旧政策，甚至查到已经撤回的文档。

先说实时一致性。这里我会把向量库当成检索副本，主文档库当成事实源。文档新增、修改、删除，先写主库，再通过 CDC 把变更送进索引流水线。CDC 是 Change Data Capture，也就是持续捕获数据库变更日志。每条事件至少带 `doc_id`、`chunk_id`、`op_type`、`source_version`、`tenant_id`、`permission_scope`、`event_time`。索引侧消费后做解析、切块、embedding、倒排更新、向量更新。关键点是要维护一个提交水位，比如 `index_watermark`。它表示“当前在线索引已经完整可查到哪个版本”。查询入口只读不超过这个水位的数据，这样一次更新要么完整可见，要么整体不可见，不会把半更新状态暴露给线上。

再说怎么避免旧知识。这里要同时处理更新和删除。更新场景下，我会给文档和 chunk 都带版本字段，比如 `doc_version`、`chunk_version`、`effective_at`。查询时先过滤当前生效版本，再做召回。删除场景下，我不会等后台把向量删干净才算生效，而是先写 tombstone。tombstone 就是删除标记，表示这条文档逻辑上已经无效。这样即使物理清理晚几分钟，查询也已经看不到它。知识库大改版时，我还会开双写窗口，新旧索引同时写一段时间，等新索引灰度通过再切流量。这样做的价值是避免 embedding 模型升级或 chunk 策略变化时，把线上召回质量一次性打乱。

最后说怎么避免脏数据。脏数据常见有三种。第一，字段不全，比如权限标签、来源系统、更新时间缺失。第二，乱序写入，旧事件比新事件晚到，结果把新版本覆盖掉。第三，部分写成功，向量更新了，倒排或元数据没更新。处理方式也对应三层。第一层是入库 schema 校验，缺字段直接拒收或进死信队列。第二层是版本比较和幂等写入，CDC 事件要按单调版本号或 LSN 判断新旧。LSN 可以理解成数据库日志里的递增序号，用来判断事件顺序。第三层是原子提交语义，至少要让“向量、倒排、元数据”这三块在查询侧看到同一版本。做不到分布式原子，就用 staged write 加提交标记，只有标记完成的版本才能被查询读到。

这里我最担心五类风险。CDC 积压会让主库和索引出现时间差；删除只做异步物理清理，旧文档还会被召回；权限变更没有进入索引流水线，用户会看到本该撤回的知识；部分写成功会制造半新半旧的结果；新老 embedding 混跑太久，向量空间分布会漂。

线上我会盯几组指标，而且每个指标都要落到故障现象。`index watermark freshness` 指当前在线水位离主库最新版本差了多少，如果这个差值持续拉大，就说明索引更新追不上主库。`delete propagation latency` 指一条删除从主库提交到检索彻底不可见花了多久，这个时间越长，召回旧知识的窗口越大。`partial write rate` 指一次文档更新里，只完成了部分索引写入的比例，这个值一上来，就容易出现向量和元数据不一致。再往效果侧看，我会盯 `stale recall rate` 和 `dirty recall rate`，前者表示召回结果里有多少已经被新版本覆盖，后者表示召回了无权限、无效状态或字段异常的 chunk。最后再补一条回放链路，把更新事件和真实 query 留下来。这样客服说“刚改的制度怎么还搜到旧的”时，能直接回放到具体版本和具体写入阶段。

### 3. 同一用户同一问题多次查询，如何做检索结果缓存？如何处理“缓存过期”与“新知识更新”的矛盾？

这题我会先讲缓存怎么做，再讲缓存过期和知识更新怎么一起处理。场景还是客服知识库。坐席连续问三次“退款规则是什么”，或者同一个用户在不同会话里反复查同一类制度，最贵的步骤通常是召回和重排，所以缓存重点要放在检索阶段。

先说缓存设计。第一层是 in-flight 去重。用户在极短时间里发出同一个请求，只让系统跑一次检索，其他请求挂到同一个 future 上等结果。future 可以理解成一个“结果占位符”，任务还没完成，但大家都能等同一份结果。第二层是检索缓存，缓存召回后的 chunk id、分数、命中的分片和 query rewrite 结果。第三层是重排缓存，缓存 topN 候选和排序分。缓存 key 至少要带 `tenant_id`、`user_id` 或 `user_scope_hash`、`normalized_query`、`filter_hash`、`conversation_scope`、`index_version`、`permission_version`、`rerank_version`。这里的 `conversation_scope` 很重要，因为同一句“这个怎么处理”在不同工单上下文里含义可能完全不同。

query 归一化也要做稳。标点、空白、时间表达、实体名、产品别名、错误码都要统一。客服知识库里，“退款规则是什么”“售后退款政策怎么走”“退货要求有哪些”很可能落到同一组检索意图。归一化做不好，缓存命中率会很差，而且命中的结果也不稳定。

再说缓存过期和新知识更新的矛盾。这里我会把版本失效放在前面，把 TTL 放在后面。每个缓存值都记录生成它时对应的 `index_version` 或 `watermark_version`，最好再带一份 `doc_versions_snapshot`，表示这次结果依赖了哪些文档版本。知识库一更新，租户级、知识库级或者分片级版本号就前进。新请求一进来，先比较版本，只要当前版本已经变了，这份缓存就直接失效。这样新知识能优先进入结果集。

TTL 还是要保留，因为版本失效只解决“知道已经更新”的情况，解决不了缓存常驻和内存占用。更新频率高但风险低的场景，我会配 `stale-while-revalidate`。它的意思是缓存刚过期时，先短时间返回旧值，同时后台异步刷新新值。这样用户不会等太久，系统也不会被刷新风暴打满。高风险知识，比如退款政策、权限制度、合规要求，我会直接绕过这套策略，只要版本变化，就强制重检索。

还有一条线必须单独管，权限变化。部门调整、角色变化、文档授权收回，都可能让昨天的缓存今天失效。所以 key 里一定要带 `permission_version`，或者把权限边界编码进 `user_scope_hash`。否则知识没更新，权限变了，缓存照样会出错。

这套缓存最容易踩的坑有四个。第一，key 不完整，跨用户、跨权限串结果。第二，失效粒度太粗，文档改一行，整租户缓存全清空。第三，失效粒度太细，该淘汰的结果没淘汰。第四，归一化规则不断变化，前后版本算出来的 key 对不上，命中率越来越低。

我会盯几组很具体的指标。`retrieval cache hit rate` 和 `rerank cache hit rate` 看缓存到底帮系统省了多少检索和重排。`stale hit rate` 看命中的缓存里，有多少已经落后于当前知识版本。`invalidation propagation latency` 看知识更新事件传到缓存失效系统花了多久，这个时间越长，旧结果继续服务的窗口越大。`permission drift miss rate` 看的是权限边界已经变化，缓存却还命中了旧结果的比例。`cache memory amplification` 看的是缓存实际占用内存和原始结果大小的比值，如果这个比值过高，说明缓存结构太重，收益和成本不匹配。上线前我会做重复 query 回放，再插入知识更新和权限变更，确认系统先命中缓存，再在该失效的时候及时失效，旧结果会被及时淘汰。

### 4. 用户问题模糊，如何做意图识别、查询改写、多路召回，提升召回率？
结论：先做意图识别和槽位补全，再做查询改写，随后并行走关键词检索、语义检索和结构化查询，最后做融合和重排。

展开：意图识别负责判断用户想查什么，槽位补全负责补出时间范围、订单状态、订单主体、业务系统等隐含条件。查询改写会把口语化问题转成更稳定的检索表达。多路召回里，BM25 适合关键词和编号匹配，向量召回适合同义表达和自然语言改写，结构化查询适合订单号、时间、状态这类强约束字段。最后用 rerank 统一排序。rerank 模型通常是 cross-encoder，也就是把 query 和候选文档拼在一起重新打分。

### 5. 表格、带格式PDF、图片文本的RAG，如何处理才能不丢失结构信息？
结论：入库阶段要做 layout-aware 解析，把文本、表格、页码、坐标、标题层级和图片区域一并抽取，chunk 设计围绕语义块和结构块展开。

展开：layout-aware ingestion 指感知版面结构的解析。PDF 里的标题、正文、表格和脚注承载的信息不同，扁平化成纯文本后，语义关系会变差。表格需要保留行列关系、表头和单元格映射；图片类内容需要 OCR，再补图像说明或人工摘要；网页内容需要保留 DOM 结构和来源链接。chunk 时可以按章节、表格块、图注块拆分，每个 chunk 保留 `source_id`、`page_no`、`bbox`、`section_path` 等 metadata。

### 6. 长文档（10w字+）RAG出现“中间内容丢失”，如何用父子分块、分层检索、重排序解决？
结论：长文档适合用父子分块和分层检索。子块负责精确命中，父块负责补语境，重排负责把真正相关的片段推到前面。

展开：单层固定切块会切断章节关系，模型只看到局部句子，很容易漏掉定义、前提和约束。父块一般对应章节或小节，包含摘要和结构信息；子块对应段落或句群，包含细粒度证据。检索时先召回子块，再回溯父块补上下文。重排阶段再对候选做精细判断。Cross-encoder 在这里很适合，因为它直接对 query-doc 对做联合编码，能更好识别上下文相关性。

### 7. 混合检索（稀疏+稠密）在生产中如何调参？如何平衡召回率与检索速度？
结论：混合检索适合按 query 类型做路由。术语、编号、专有名词类请求优先走稀疏检索，语义改写类请求优先走向量检索，融合层用 RRF 或加权分数。

展开：BM25 是经典稀疏检索模型，基于词项频率和文档长度做相关性评分。稠密检索依赖 embedding，把文本映射到向量空间。RRF 是 Reciprocal Rank Fusion，按排名位置融合多个检索器的结果，稳定性高。调参时先看 query 分布，再看召回命中率、误召回率和延迟曲线。简单 query 走轻路径，复杂 query 走重路径。

### 8. RAG与多轮对话结合，如何实现“基于历史上下文的自动检索”？避免重复检索、无效检索？
结论：系统要维护会话级证据状态，当前轮是否触发检索由主题变化、实体变化、事实更新和证据覆盖率共同决定。

展开：多轮场景里，不能把每轮都当成新问题。系统需要记录当前主题、已确认实体、已使用证据、最近一次检索 query 和检索时间。当前轮如果只是继续追问，优先复用已有证据；如果主题切换，才触发新的 query rewrite 和检索。这个机制常叫 retrieval trigger。它的价值在于减少重复召回，也避免把历史上下文和当前问题混在一起。

### 9. 如何避免RAG检索到大量无关片段，导致LLM回答跑偏？
结论：要从切块、查询、过滤和重排四处一起治理，并在生成阶段要求证据绑定。

展开：先看 chunk 质量，chunk 太大时主题会混杂；chunk 太小时证据会碎裂。再看 query rewrite，用户问题改写不到位，召回集合会很脏。metadata filter 能先过滤掉时间、权限、类型不匹配的内容。MMR 是 Maximal Marginal Relevance，中文可以理解成最大边际相关性，它会在相关性和多样性之间做平衡，防止候选结果过度重复。生成时要求答案引用证据，缺证据时返回拒答或澄清问题。

### 10. 生产环境如何自动化评估RAG效果？
结论：评估要拆成检索评估和回答评估两层，同时补上时延和成本指标。

展开：检索层常看 Recall@K、MRR、NDCG 和过滤准确率。MRR 是 Mean Reciprocal Rank，关注第一个正确结果出现得有多靠前。回答层常看 relevancy、faithfulness、citation precision、拒答正确率。`faithfulness` 指答案是否忠实于检索证据。线上评估可以加人工抽检、用户反馈和 shadow traffic。评测集要覆盖失败样本、长文档、模糊问题、权限受限问题和更新滞后问题。

### 11. Embedding模型如何选型？中英文文档混合场景，如何选择合适的Embedding模型，平衡效果与速度？
结论：选型主要看跨语种对齐、领域适配、向量维度和吞吐成本。中英文混合场景要优先验证跨语种 query-doc 对齐能力。

展开：Embedding 是把文本映射到向量空间的模型，向量接近表示语义接近。中英文混合场景里，常见问题是中文 query 是否能命中英文文档，反过来也一样。评测时要专门构造跨语种样本。向量维度越高，表达能力通常越强，索引体积和检索开销也会上升。速度要求高时，可以选更小维度或更轻量模型，再配合缓存和分层索引。

### 12. 向量检索中，余弦相似度、点积、欧氏距离的实际应用差异？如何选择？
结论：三者衡量相似性的方式不同。余弦相似度看方向，点积看方向和长度，欧氏距离看空间距离。文本检索里，常见选择是余弦或归一化后的点积。

展开：如果向量做过 L2 归一化，余弦和点积的排序往往接近。余弦适合关注语义方向的一般检索场景；点积在模型训练目标和在线索引设计一致时很常见；欧氏距离更接近几何距离，文本检索里使用频率低一些。选型时先看 embedding 模型的训练目标，再看向量库支持的索引和打分方式。

### 13. RAG的rerank重排环节，如何选择重排模型？如何优化重排速度？
结论：重排模型优先看排序质量，再看延迟。常见方案是 cross-encoder，候选数量较多时先召回，再对 topN 做精排。

展开：cross-encoder 会把 query 和文档一起输入模型，适合做高精度相关性判断，代价是推理慢。双塔模型推理快，精度通常低一些，适合大规模召回。速度优化常用批量化、半精度、动态 topN 和 query routing。query routing 指按 query 难度决定是否启用重排。热点 query 可以缓存重排结果，减少重复计算。

### 14. 动态知识更新场景（如每日新增文档），RAG如何设计增量更新机制，避免全量重新向量化？
结论：更新链路按 chunk 粒度做增量处理，内容哈希、embedding 模型版本和 chunk 策略版本都要纳入索引元数据。

展开：全量重建的成本会随文档规模线性上升，增量更新更适合在线业务。文档到来后先做解析和切块，对每个 chunk 计算 content hash，和历史版本比对；有变化的 chunk 重新 embedding，没有变化的 chunk 直接复用。索引里保留 `parser_version`、`embed_model_version`、`chunk_policy_version`，模型升级后能知道哪些向量需要重建。删除走软删和异步清理，减少索引抖动。

### 15. 如何处理RAG中的噪声文档（如无效文档、重复文档）？如何做文档去重、过滤？
结论：噪声治理适合前移到入库阶段。先做格式校验、近似去重和来源分级，再进入索引。

展开：噪声文档会稀释召回结果，也会拖累重排。精确去重可以用内容哈希，近似去重可以用 MinHash 或 SimHash。MinHash 适合估算集合相似度，SimHash 适合做文本指纹。再结合来源可信度、更新时间和文档长度做过滤。重复内容多的知识库，检索出来的候选会高度同质，模型更容易跑偏。

### 16. RAG服务高并发下，如何做负载均衡、水平扩展？
结论：检索、重排、生成适合拆成独立服务，各自扩容。检索层尽量无状态，前面挂分片路由和缓存，重排与生成按 CPU/GPU 资源池独立治理。

展开：无状态服务更容易水平扩展，状态放到外部存储、缓存和队列里。分片路由负责把请求打到目标向量分片，减少跨节点通信。热点分片要单独治理，避免某个 shard 被打满。背压机制也要有，队列积压到阈值时触发限流或降级。高并发里，尾延迟比平均延迟更重要。

### 17. RAG与Fine-tuning在生产中如何选型？什么场景下优先用RAG，什么场景下需要微调？
结论：知识频繁变化、需要引用来源、涉及私有数据时，RAG 更合适；输出风格稳定、任务模式固定、行为模式需要固化时，微调更合适。成熟系统里，两者经常同时使用。

展开：RAG 解决知识接入和可追溯问题，微调解决行为习惯和输出格式问题。知识类内容变化快，适合走检索；行为类模式，例如客服话术、分类风格、结构化抽取格式，适合用微调固化。组合方案里，模型先用微调掌握行为，再通过 RAG 补充事实。

### 18. 如何解决RAG的“检索滞后”问题？
结论：要把知识新鲜度做成 SLA，查询协议里带版本号，索引更新走增量刷新，主存和向量索引之间保留回源路径。

展开：检索滞后多出现在主存已更新、索引尚未刷新这段窗口。处理方式是先更新主存，再触发增量 embedding 和索引刷新，查询时优先命中最新可见版本。如果向量索引追不上，可以临时回查主存或热索引。版本可见性很关键，能让查询知道当前看到的是哪个快照。

## 四、LLM工程化与高并发、稳定性

### 1. 峰值QPS 100+的LLM接口，如何做排队、削峰、批量推理、优先级调度？
结论：我会按 token 预算调度请求，把排队、批处理、优先级、取消放在同一条链路里处理。

展开：入口先做 admission control，按租户、任务等级、预估上下文长度、预估输出长度分队列；推理层用 continuous batching 合并不同请求的 prefill 和 decode，提升 GPU 利用率。监控重点看 TTFT、TPOT、队列深度、单卡 token/s、拒绝率和取消率。积压上升时，先收紧长上下文和低优先级流量，再把部分请求切到小模型或异步队列。`TTFT` 指 first token latency，首 token 延迟；`TPOT` 指 time per output token，每个输出 token 的平均时间。

### 2. LLM推理加速方案（vLLM、TGI、TensorRT-LLM）的原理与落地差异？如何选择？
结论：三者的差异主要落在 KV cache 管理、批处理方式、kernel 优化深度。

展开：vLLM 的核心是 PagedAttention，它把 KV cache 按页管理，降低显存碎片，适合在线多请求推理；continuous batching 让新请求持续进入批次，提升吞吐。TGI 更像标准化服务层，部署和生态接入顺手。TensorRT-LLM 偏向极致性能，通常依赖固定模型、固定硬件和更强的工程投入。选型时先看模型兼容性，再看单位 GPU 吞吐、延迟曲线和运维复杂度。

### 3. 模型量化（INT8/INT4/FP8）的原理？生产中如何平衡量化精度与推理速度？量化后的坑如何规避？
结论：量化是在数值精度、显存占用、带宽压力之间做折中。

展开：INT8 和 INT4 主要降低权重或激活的表示精度，FP8 属于更细粒度的低精度格式，通常保留更好的数值稳定性。生产里先做校准集评估，看 perplexity、任务成功率、长上下文稳定性、工具调用成功率，再看吞吐和显存收益。常见坑包括长序列退化、个别层对低比特特别敏感、量化后输出分布偏移。处理方式可以是分层量化、保留敏感层高精度、对业务集做回归评测。

### 4. 模型API突然报错、限流、宕机，后端如何设计熔断机制、切换备用模型？如何保证用户无感知？
结论：模型访问层适合做成统一网关，健康检查、熔断、切流都在这一层完成。

展开：网关持续采集错误率、超时率、429 比例、TTFT 异常，一旦越过阈值，就把流量切到备用模型或备用供应商。切换前要保证 Prompt 模板、输出协议、解析逻辑一致。用户侧保持统一返回格式，失败时保留已生成内容和明确状态，避免页面出现断裂感。高价值请求可以加人工兜底或延迟重试。

### 5. 如何防止恶意用户构造超长上下文、高频请求，刷Token造成成本暴增？
结论：请求进入模型前做预算控制。先估算 prompt token 和预估 completion token，超过租户预算直接拒绝或截断。

展开：网关层按用户、租户、IP、功能维度限流，后台再看异常模式，例如短时间重复提交、上下文异常膨胀、输出极长。对重复问法、超长上下文、异常高频请求做风控评分。必要时把部分流量降级到小模型，或者把长任务转成异步队列。

### 6. 生产中如何实现多模型调度？如何设计调度策略？
结论：调度策略先看任务类型，再看置信度，再看成本预算。

展开：分类、改写、抽取、轻问答交给小模型，复杂推理、跨文档整合、高风险决策交给大模型。路由层可以用规则、轻量分类器、置信度阈值组合起来做，低置信或解析失败时升级模型。线上留一条 shadow 流量，持续对比不同模型在成功率、时延、成本上的表现，再调权重。

### 7. LLM推理服务GPU资源有限，如何做资源隔离、队列优先级、超时抢占？
结论：按业务池和优先级池切分 GPU 资源。

展开：P0、普通请求、批处理请求放到不同队列，分别设并发上限和 token 预算。抢占动作只发生在安全点，例如请求尚未入批、chunk 边界、或任务处于可恢复状态，避免中途打断造成状态泄露。监控层重点看 KV cache 占用、显存碎片、排队时长、长尾请求比例。资源紧张时，先收紧低优先级和长上下文任务。

### 8. 异步Agent任务（执行时间>10s）如何设计？
结论：长任务适合用显式状态机管理。前台只返回 `task_id`、当前状态、结果查询方式。

展开：后台保存任务状态、步骤日志、checkpoint、中间产物、最终结果。重试按步骤粒度做，写操作配幂等键，读操作按业务容忍度重试。结果通知可走 webhook、轮询、SSE 或消息队列。落库至少保留 `task / step / event` 三层数据，方便回放、审计和问题定位。

### 9. 如何实现LLM请求全链路压测？如何模拟真实对话流量、流式请求场景？
结论：压测要按真实流量画像回放。

展开：先抽样得到上下文长度分布、输出长度分布、流式占比、工具调用比例、租户分层，再生成混合负载。指标看 TTFT、TPOT、token/s、错误率、队列积压、取消率和尾延迟。还要单独测异常场景，例如上游 429、客户端断连、模型慢响应、部分流中断。这样得到的数据更接近线上真实表现。

### 10. 微服务架构下，AI模块与Java/Go后端如何实现分布式事务、最终一致性？
结论：AI 模块放在编排层，业务事务继续留在后端主链路。

展开：写入型流程先落 intent，再通过 outbox 或事件驱动触发 AI 处理，完成后回写状态。失败时走补偿动作或人工接管。这里的核心是把副作用收束在边界内，把一致性问题转成最终一致性问题。这样系统能接受 LLM 的不确定性，业务状态仍然可控。

### 11. Agent服务如何高可用部署？多实例、负载均衡、灾备设计的核心要点？
结论：高可用的前提是服务尽量无状态，状态外置。

展开：API 层多实例部署，前面挂负载均衡和健康检查；任务状态、记忆、日志、审计、队列放在外部存储。发布时做灰度和回滚，模型层准备主备切换和跨区域容灾。核心动作只有四个：切流、重试、回放、降级。缺少这四个，副本数量再多也只是表面高可用。

### 12. 如何做LLM结果、Embedding、检索结果的缓存设计？如何设置缓存过期时间？
结论：缓存要按对象类型设计。

展开：Embedding 用 `content_hash + model_version` 做 key，适合长缓存；检索结果用 `normalized_query + filter + index_version` 做 key，主要靠版本失效；生成结果只缓存低随机、低个性化场景，并绑定 prompt 版本。TTL 只是兜底，主失效机制依赖版本号。这样能减少重复计算，也能控制知识更新后的脏命中。

### 13. 日志量巨大（每轮对话10KB+），如何设计存储、检索、审计、降冷方案？
结论：日志分热、温、冷三层。

展开：热层保结构化字段、错误摘要、trace id，支撑检索和告警；温层保关键原文和失败样本；冷层把全量事件沉到对象存储或归档系统。入库前先做脱敏、采样、字段裁剪，避免把原文全量灌进 ES。审计和业务日志分开存，审计日志更强调不可篡改和可追溯。

### 14. 如何做权限控制？如何避免Agent越权操作？
结论：权限控制放在后端策略层。数据权限控制可见范围，工具权限控制可执行动作，功能权限控制可触发能力组合。

展开：模型只接收被裁剪后的上下文，不接触原始凭证。高风险动作走审批、双人确认或只读默认。策略引擎支持租户、角色、资源、动作四个维度的判定，审计链完整保留。

### 15. Docker + K8s部署Agent/LLM服务，需要注意哪些点？
结论：资源配置要把 CPU、内存、GPU 的 request 和 limit 写清楚，避免调度失真。

展开：健康检查要区分 `startupProbe`、`readinessProbe`、`livenessProbe`，模型 warm up 前不接流量。滚动更新要支持优雅停机，确保流式请求能收尾。GPU 场景还要关注节点亲和、驱动版本、共享存储、镜像体积和启动时间。

### 16. MLOps如何应用在Agent系统？
结论：Agent 系统里的 MLOps 要覆盖模型、Prompt、工具、路由规则、评测集和策略配置。

展开：每次变更都应有版本号、回滚点、灰度流程和自动回归。线上指标至少看任务成功率、成本、时延、安全命中率、人工接管率。失败样本要回流到评测集，形成持续修正闭环。这样系统迭代时，行为变化可追踪，问题可定位。

## 五、安全、成本与架构设计

### 1. Prompt Injection攻击的原理与生产级防御方案？
结论：Prompt Injection 的核心问题，是外部文本试图获得比系统指令更高的解释权。

展开：防御层先做信任边界划分，把系统指令、用户输入、检索文档、工具返回分层处理；模型默认把外部内容当数据。执行层再加工具白名单、动作审批、敏感操作校验、注入检测。这里的重点是系统约束，Prompt 只是其中一层。

### 2. 如何防止敏感信息进入LLM，造成数据泄露？
结论：模型调用前做字段级脱敏和最小暴露。

展开：PII 检测先识别手机号、身份证号、订单号、地址等字段，再替换成占位符；需要回填展示时，在模型外做映射恢复。日志、缓存、评测集、trace 也要同步脱敏。外部模型接口还要配合零留存、访问审计和地域合规，避免敏感数据扩散到旁路系统。

### 3. 生产中如何控制Token消耗与模型成本？
结论：成本控制先从 token 控制开始。

展开：上下文摘要、证据裁剪、重复 query 折叠、小模型前置路由、批量 embedding、输出长度上限，这些动作都直接减少 token 消耗。再叠加租户预算、功能预算、异常告警，成本就能落到可见范围。成本按租户、功能、Prompt 模板、模型版本四个维度拆开看，定位会更快。

### 4. 私有部署vs API调用如何选型？各自的成本、稳定性、安全性对比？落地场景是什么？
结论：选型看数据主权、时延要求、调用规模和运维能力。

展开：私有部署适合对数据隔离、稳定性和可控性要求高的场景，API 调用适合追求接入速度和模型能力更新的场景。私有部署的成本集中在算力、推理工程和运维，API 的成本集中在调用费用和供应商依赖。很多系统最后采用混合方案，核心数据本地化，通用能力走外部 API。

### 5. 如何保证Agent行为可解释、可审计、可回溯？
结论：可解释性来自事件记录，不来自事后复述。

展开：每次执行都要记录输入摘要、状态变化、工具调用、模型版本、Prompt 版本、权限决策、最终动作和时间线。链路层挂 trace id 和 run id，日志层保留事件流，审计层保留不可篡改记录。这样任何行为都能回放，任何问题都能追到具体步骤。

### 6. 设计一个企业内部知识库问答Agent，架构图+核心流程+性能优化点？
结论：架构分四层：接入层、索引层、编排层、治理层。

展开：接入层负责文档解析、权限同步、增量更新；索引层负责切块、embedding、混合检索和版本管理；编排层负责 query rewrite、retrieval、rerank、答案生成和引用返回；治理层负责缓存、评测、日志、审核和权限。性能优化重点放在权限预过滤、热点缓存、增量索引、按需重排和证据窗口裁剪。

### 7. 设计一个Text2SQL Agent，如何解决SQL注入、表结构识别、复杂查询问题？
结论：Text2SQL 的关键是把模型放进受控语义层。

展开：模型看到的是裁剪后的 schema、字段说明、业务别名、join 关系、示例 SQL；生成后要过 AST 校验、权限校验、成本估算和只读执行。多表关联可以通过视图、指标层、模板查询来收紧自由度。这样做能把 SQL 注入风险压低，也能让复杂查询更稳定。

### 8. 设计一个客服多Agent系统，如何实现意图识别、知识库检索、工单生成、人工转接的无缝衔接？
结论：我会用 supervisor 统一调度多 Agent。

展开：入口先做意图识别、风险评分、实体抽取，再分流到知识 Agent、工具 Agent、工单 Agent 或人工。状态、证据、已执行动作、转接原因都要统一记录。人工接管要继承上下文和审计链，避免用户重复描述，也避免处理过程失真。

### 9. 设计一个低延迟、高并发的RAG服务，核心架构与性能优化点？
结论：架构拆成网关、查询理解、检索、重排、生成、观测六段，各段独立扩缩容。

展开：低延迟靠 query cache、权限预过滤、分片路由、ANN 检索、按需重排和证据裁剪；高并发靠无状态服务、队列背压、多级缓存和热点分片治理。百万级文档场景里，版本化索引和增量更新是基础，分片策略决定尾延迟。

### 10. 如何设计多Agent协作系统？结合内容创作场景实操？
结论：多 Agent 协作适合工件驱动。

展开：内容创作场景可以拆成选题、资料搜集、提纲、初稿、事实校验、风格编辑几个角色，每个角色输入和输出都结构化。supervisor 负责调度和验收，冲突规则提前定义，例如事实校验拥有覆盖权，风格编辑只处理表达。这样协作链路清楚，问题也容易定位。

### 11. 从后端工程师角度，如何搭建可上线的Agent平台？
结论：平台要覆盖接入网关、身份与权限、模型网关、Agent 编排、工具运行时、记忆与 RAG、调度与任务、观测评测、运营控制台九个模块。

展开：技术选型优先看边界、稳定性和可替换性，避免把系统绑死在单一框架默认行为上。工程保障包括幂等、限流、回放、灰度、审计、安全沙箱、自动评测。这样平台才能承载真实业务。

### 12. 如何做输出内容审核、毒性检测？如何避免Agent生成违规、不当内容？
结论：审核要做成独立服务，前后双向拦截。

展开：输入侧做越狱检测、风险分类、意图识别；输出侧做毒性、违法、隐私、歧视检测。流式场景按 chunk 增量审核，命中规则立即截断。高风险请求直接拒绝，中风险请求走降级模板或人工复核。策略要版本化，方便回归和追责。

### 13. 灾备设计：主模型/主服务挂了，如何自动切换到备用，不影响用户体验？
结论：灾备要先定义触发阈值，再设计切换动作。

展开：路由层持续监控错误率、超时率、心跳失败数，一旦超过阈值就摘流并切到备用模型。状态放在外部系统里，保证切换后能延续对话和任务。演练要定期做，覆盖模型、路由、状态、日志四个层面。

### 14. 设计一个自动化运维Agent，如何实现日志读取、问题定位、命令执行、异常提醒？
结论：运维 Agent 按风险分层开放能力。

展开：第一层只读，负责查日志、查指标、查配置、画依赖图；第二层生成变更建议和执行计划，等待审批；第三层才开放受控命令执行，并放在沙箱、白名单和回滚机制里。这样能缩短 MTTR，也能保住变更治理。

### 15. 多模型服务网格如何设计？如何实现模型的动态切换、负载均衡、健康检查？
结论：模型网格统一收敛到模型网关，对外只暴露一致协议。

展开：网关维护模型注册表、能力标签、成本、延迟、可用性、健康状态，根据任务类型、SLO、预算和实时健康做动态路由。负载均衡要同时看请求数和 token 压力。这样模型可切换，业务协议可稳定。

### 16. 如何处理Agent执行过程中的“长尾任务”？如何优化性能、控制成本？
结论：长尾任务先识别，再拆分，再异步化。

展开：入口先估算复杂度和资源预算，超预算任务默认走后台队列和 checkpoint 执行；中间产物尽量缓存，重复子任务做复用，必要时拆成多个可回收阶段。性能优化靠拆任务，成本控制靠预算和复用。

## 一、流式输出

### 1. 前端实现大模型流式输出，SSE与WebSocket选型逻辑是什么？各自优缺点、适用场景是什么？
结论：单向文本流优先 SSE，双向交互、控制事件、协同编辑优先 WebSocket。

展开：SSE 基于 HTTP，穿透网关和代理更顺，客户端实现也更轻，适合聊天正文、答案增量返回、状态推送。WebSocket 提供双向消息通道，适合前端发取消、补参、确认、同步控制信号。选型时先看消息方向，再看现有基础设施，再看端侧兼容性。高并发场景里，SSE 的运维模型通常更简单，WebSocket 的协议表达能力更强。

### 2. 流式返回过程中网络中断、前端重连，后端如何恢复上下文继续输出？如何避免重复输出、丢包？
结论：恢复流式输出依赖稳定的 `run_id`、递增 `seq`、客户端确认位点。

展开：服务端把已发送的 chunk 和事件暂存，客户端重连时带上 `Last-Event-ID` 或最后确认序号，后端只补发后续内容。每个事件都带 `run_id`、`seq`、`finish_reason`，前端可以去重，后端可以回放。底层模型如果不支持真正续采样，系统层面仍然可以恢复用户可见进度，避免重复展示和内容缺口。

### 3. 用户点击“停止生成”，后端如何立即终止LLM推理、释放GPU/CPU资源？如何避免资源泄露？
结论：停止生成要走完整的取消链路。

展开：前端发出 cancel 以后，网关、编排器、推理服务都接收同一个 cancellation token，在安全点停止生成。资源释放要进入统一清理路径，包含 KV cache、流对象、队列占位、临时上下文。用户层面看到的是“当前回答停止”，系统层面保留的是干净状态和可继续执行的会话记录。

### 4. 流式返回时，如何插入非文本事件，且不影响前端渲染？
结论：把输出定义成事件流，文本和系统事件分开。

展开：每个事件带 `type`、`seq`、`payload`、`ts`，常见类型包括 `token`、`tool_call`、`tool_result`、`warning`、`error`、`done`。前端按类型分别渲染，文本内容进正文区，工具调用进操作区，错误进提示区。思考过程如果需要展示，建议使用受控的 `reasoning_summary` 事件，保留摘要级信息，避免把内部推理直接暴露成长文本。

### 5. 多轮对话+流式输出，如何保证消息不乱序、上下文不丢失？跨服务流式透传如何实现？
结论：同一轮回复绑定唯一 `message_id` 和 `stream_id`，所有事件按 `conversation_id + turn_id + seq` 排序。

展开：上游服务负责会话状态、顺序控制和持久化，下游模型服务负责按协议发事件。跨服务透传可以用 HTTP chunked、gRPC stream 或消息总线。关键点是单写原则：状态先落库，再对前端可见。这样链路中断时，系统能恢复到最近的稳定位点，消息顺序也能保持。

### 6. 高并发下，大量SSE长连接如何做连接复用、心跳检测、超时释放？避免OOM的核心优化点是什么？
结论：SSE 长连接要控制每条连接的状态占用。

展开：连接层可以通过 HTTP/2 复用 TCP 连接，网关层负责连接数上限、空闲超时、心跳保活和慢客户端摘除。每条连接只保留轻量对象和固定大小缓冲，避免挂载大上下文和大队列。OOM 的常见来源是连接对象膨胀、缓冲堆积、未释放的发送队列，这些点都要在服务端收紧。

### 7. 流式输出场景中，如何实现内容安全实时截断？
结论：内容安全要做增量审核。

展开：流式输出按 chunk 或滑动窗口进入规则引擎和审核模型，命中高风险内容后立即发终止事件，停止后续生成。系统需要保留风控原因、会话状态、命中片段和处置结果，便于审计和回放。对高风险会话，还要根据策略清理上下文或标记风险状态。

### 8. 流式返回时，如何精准统计Token消耗，适配计费场景？
结论：计费以最终 usage 为准，实时展示可以用 tokenizer 估算。

展开：流式过程中记录预估 prompt token、预估 completion token、chunk 数和输出长度，请求结束后再用模型返回的正式 usage 对账。若存在缓存命中、重试、截断，也要一并记录。这样既能支持前端实时显示，也能让计费结算保持准确。

### 9. 小程序、APP、PC端对流式输出的兼容性差异如何处理？如何解决部分端流式渲染卡顿问题？
结论：先统一协议，再做端侧适配。

展开：SDK 层抽象 `connect / parse / ack / cancel / resume`，不同端只处理各自的传输实现。兼容 SSE 的端走 SSE，兼容性一般的端走 WebSocket 或分片轮询。渲染层按时间片或 chunk 批量刷新，避免每个 token 都触发 UI 重绘。这样可以降低卡顿，也能让各端表现一致。

### 10. 流式推理时，LLM模型报错，如何设计兜底策略，保证用户体验？
结论：保留已生成内容，返回结构化错误，给出继续执行路径。

展开：服务端在中途报错时发送错误事件，前端保留已生成文本和失败原因。若当前上下文可复用，系统可以切到备用模型续写；若上下文已经失效，就返回明确的重试入口或人工接管入口。用户看到的是可解释的失败结果，系统保留的是可恢复状态。

### 11. 如何实现流式输出的“断点续打”？用户刷新页面后，如何恢复之前未完成的流式内容？
结论：断点续打依赖事件日志、运行状态、客户端确认位点。

展开：服务端记录每个 chunk 的序号、时间戳和状态，客户端刷新后先拉取已确认片段，再继续订阅后续事件。如果 run 仍在执行，系统从 `last_seen_seq` 继续推送；如果 run 已结束，就返回终态和完整可见内容。这样可以保住用户体验，也能保住服务端状态一致性。

### 12. 跨服务流式透传时，如何做日志埋点，支撑全链路追踪？
结论：埋点围绕事件流展开。

展开：每段输出记录 `first_token_latency`、chunk 数、每段时间戳、总 token、异常码、结束原因、取消来源，再统一挂到 `trace_id` 上。内容本身只保留摘要或抽样，避免日志量过大。这样既能定位卡顿、断连、超时，也能做成本统计和回放分析。

## 六、补充题

### 1. 如果知识库原始数据不是 markdown，而是 PDF、PPT、图片或者网页，你会怎么处理进 RAG 系统？
结论：先进入统一的 ingestion pipeline，再进入索引层。

展开：PDF、PPT、网页、图片分别做正文抽取、版面解析、OCR 和结构保留，保留标题层级、页码、来源、时间、权限、表格结构、图片说明这些字段。随后按文档类型切块、做质量校验、打版本号、写入索引。RAG 的稳定性很大一部分取决于这一步。

### 2. 在 RAG 检索过程中，常用的检索机制有哪些？
结论：常见机制有稀疏检索、稠密检索、混合检索、元数据过滤、重排。

展开：BM25 这类稀疏检索适合实体词、术语、编号和精确匹配；向量检索适合语义改写和同义表达；混合检索把两者合并；metadata filter 负责按权限、时间、类别先筛一遍；rerank 负责在少量候选里重新排序。复杂业务里还会叠加 SQL 检索、图谱检索和规则路由。

### 3. RAG 评价指标一般怎么设计？
结论：评价分检索层和回答层。

展开：检索层关注 Recall@K、MRR、NDCG、过滤命中率，回答层关注 relevancy、faithfulness、citation precision、拒答正确率，再补时延、成本、重试率。`Recall@K` 看正确证据是否进入候选集，`faithfulness` 看回答是否依托证据，`citation precision` 看引用是否准确。评测集要来自真实问题和失败样本。

### 4. 为什么很多场景会优先选 RAG，而不是直接微调大模型？
结论：RAG 适合变化快、需要可追溯、需要独立更新的知识场景。

展开：知识放在外部索引里，更新速度快，回滚路径清晰，审计也更直接。微调更适合固化输出风格、任务格式和行为偏好。企业系统里常见的组合是，模型负责生成和推理，RAG 负责事实来源。

### 5. MCP 和 Function Call 的区别是什么？
结论：Function Call 处理单次工具调用，MCP 处理工具和资源的标准接入。

展开：Function Call 定义的是模型如何输出结构化参数，以及工具如何接收这些参数。MCP 定义的是工具、资源、提示如何被发现、鉴权、调用和传输，常见传输方式包括 stdio、HTTP、SSE、WebSocket。前者偏执行协议，后者偏能力生态。

### 6. 为什么 AI 应用里经常需要做两级缓存？
结论：两级缓存对应两类热点。

展开：进程内缓存保存最热、最短路径的数据，例如 tokenizer、Prompt 模板、热点 embedding；Redis 这类共享缓存服务多实例复用，减少重复检索、重复生成、重复向量化。这样可以同时控制延迟、成本和多实例一致性。缓存 key 需要带上模型版本、Prompt 版本、知识版本。

### 7. 如果要做一个智能客服类 AI 应用，整体链路怎么设计？
结论：客服系统适合做成分流式链路。

展开：入口先做身份识别、意图分类、风险评分和实体抽取，再把请求分到 FAQ、RAG、工具调用、工单、人工转接几条路径。治理层负责权限、内容审核、日志、评测、回放和转人工。客服系统最重要的指标是错误时是否可控、是否可接管、是否可追责。

### 8. 为什么有些场景会选 PGVector，而不是直接用 ES 做向量检索？
结论：业务主数据已经在 PostgreSQL，且规模和复杂度适合单库管理时，PGVector 更顺手。

展开：它把结构化数据、权限、事务和向量放在同一套数据库里，开发和运维都更直接。ES 更适合全文检索、复杂搜索和大规模分布式检索。选型时看主诉求：业务一体化、事务一致性、搜索能力上限。

### 9. MySQL 和 Elasticsearch 的区别是什么，AI 应用里怎么分工？
结论：MySQL 负责事务型主数据，Elasticsearch 负责搜索和分析。

展开：AI 应用里，MySQL 常存用户、权限、配置、任务状态、业务记录；ES 常存检索索引、搜索辅助字段、可查询日志。两者的边界很清楚，前者承载一致性，后者承载检索效率。

### 10. 为什么 Elasticsearch 要使用倒排索引，而不是顺序扫描？
结论：倒排索引把“词 -> 文档集合”的映射提前建好，查询时直接定位候选文档。

展开：顺序扫描面对大规模文档时，代价会迅速上升。倒排索引配合 BM25、短语查询、布尔过滤，能把大规模文本检索控制在可接受延迟内。它是搜索系统里最基础的性能结构。
